Chapitre 4 : Sprint 2 – Gestion des Projets
Introduction
Dans ce chapitre, nous présentons les démarches réalisées pour l’atteinte des objectifs du deuxième sprint, qui couvre la création et la gestion des projets, ainsi que l’affectation des membres à ces projets. Ces éléments de modélisation permettent de formaliser les interactions entre les acteurs du système et les fonctionnalités développées.

2. Analyse et Conception
2.0. Règles métier et cycle de vie du projet
Le cycle de vie d’un projet suit une progression stricte en trois statuts, décrits dans le tableau ci-dessous.
Statut
Déclencheur
Description
ouvert
Création du projet
Statut initial défini automatiquement à la création par le chef de projet ou l’admin.
en_cours
Premier ticket créé par un testeur
Le système passe automatiquement le projet en « en_cours » dès qu’un testeur soumet un premier ticket.
fermé
Fermeture volontaire par le créateur
Possible uniquement si tous les tickets du projet ont le statut VALIDE. Le projet est archivé avec son historique complet.
Tableau 2 — Cycle de vie d’un projet
Les règles métier fondamentales régissant ce module sont les suivantes :
Un chef de projet peut créer, modifier et fermer uniquement les projets qu’il a créés.
Un admin hérite de toutes les capacités d’un chef de projet et peut consulter l’ensemble des projets de la plateforme ; il ne peut modifier ou fermer que ses propres projets.
La fermeture d’un projet est conditionnelle : tous les tickets du projet doivent avoir le statut VALIDE.
Un projet fermé est archivé avec son historique complet : date_debut, date_fin, membres participants, créateur, nombre de tickets.
La suppression d’un projet est interdite (HTTP 403) pour garantir la traçabilité.
Un seul testeur peut être affecté à un projet. Plusieurs développeurs peuvent être affectés simultanément.
Toute modification du projet (membres ou informations) déclenche une notification à tous les membres affectés.
Le passage automatique au statut « en_cours » s’effectue lorsqu’un testeur crée le premier ticket.

Cas d’utilisation : Créer un projet
Sommaire d’identification
Titre
Créer un projet
Description
Ce cas décrit le processus de création d’un nouveau projet par un chef de projet ou un administrateur sur la plateforme.

Un message de confirmation est affiché.
Enchaînements alternatifs / Erreurs
E1 : Nom vide → « Le nom du projet est obligatoire. » E2 : Nom déjà utilisé → « Un projet avec ce nom existe déjà. »

2.2.3. Cas d’utilisation « Fermer un projet »
Cas d’utilisation : Fermer un projet
Sommaire d’identification
Titre
Fermer un projet
Description
Ce cas décrit la fermeture et l’archivage d’un projet lorsque tous ses tickets sont validés.
Acteurs
Chef de projet (créateur), Admin (créateur)
Description des enchaînements
Pré-condition
Le projet est en statut « ouvert » ou « en_cours ». L’acteur est le créateur. Tous les tickets du projet ont le statut VALIDE.
Post-condition
Le statut du projet passe à « fermé ». Le projet est archivé avec : date_debut, date_fin (date de fermeture), liste des membres ayant participé, identité du créateur, nombre total de tickets. Aucun nouveau ticket ne peut être ajouté.
Scénario nominal
1. L’acteur clique sur « Fermer le projet ». 2. Le système vérifie que tous les tickets sont en statut VALIDE. 3. Le système passe le statut à « fermé » et enregistre la date_fin. 4. Le projet apparaît en lecture seule dans la liste archivée avec son historique complet. 5. Un message de confirmation est affiché.
Enchaînements alternatifs / Erreurs
E1 : Des tickets ne sont pas encore VALIDE → « Impossible de fermer : X ticket(s) ne sont pas encore validés. » E2 : Acteur non créateur → HTTP 403 « Accès refusé. »

Cas d’utilisation : Affecter des membres à un projet
Sommaire d’identification
Titre

Un message de confirmation est affiché.

Le système supprime l’association et envoie une notification au membre retiré.

3. Diagrammes de séquence
Les diagrammes de séquence permettent la modélisation dynamique d’un système en langage UML. Ils décrivent les interactions temporelles entre les différents composants (acteur, vue, contrôleur, modèle, système de mailing) pour réaliser un cas d’utilisation donné. Chaque flèche pleine représente un appel, et chaque flèche en pointillé représente un retour.
Pour ce sprint, trois diagrammes de séquence ont été réalisés, correspondant aux scénarios dont la logique métier est la plus complexe et la plus représentative du module.

4. Diagramme de classe
Un diagramme de classe est un type de diagramme UML qui décrit la structure statique d’un système en représentant les classes, leurs attributs, leurs méthodes et les relations qui existent entre elles. Il constitue la base de la conception orientée objet et guide la création des modèles de la base de données.
La figure ci-dessous illustre le diagramme de classes élaboré pour le Sprint 2, centré sur le module de gestion des projets, des affectations et des notifications.

Structure de la classe Project :  id · nom · description · statut (ouvert | en_cours | fermé) · created_by (FK → User) · date_debut · date_fin · timestamps
Table pivot project_user :  project_id (FK → Project) · user_id (FK → User) · created_at
Relations :  Project belongsTo User (created_by)  ·  Project belongsToMany User (members)  ·  User belongsToMany Project  ·  Project hasMany Ticket  ·  Ticket belongsTo Project

5. Revue du Sprint 2
Cette section présente les résultats obtenus à l’issue du deuxième sprint, illustrés par les interfaces développées de l’application.
5.1. Interface de Création d’un Projet
L’interface de création permet au chef de projet ou à l’admin de saisir le nom et la description du projet. Le statut « ouvert » est attribué automatiquement à la création.
Figure 6 — Interface de création d’un projet
5.2. Interface de Modification d’un Projet
L’interface de modification affiche le formulaire pré-rempli avec les données du projet sélectionné. Seul le créateur du projet peut accéder à cette interface.
Figure 7 — Interface de modification d’un projet
5.3. Interface de Fermeture d’un Projet
L’interface de fermeture déclenche la vérification conditionnelle de tous les tickets. Si la condition est remplie, le projet est archivé et passe en lecture seule.
Figure 8 — Interface de fermeture d’un projet
5.4. Interface d’Affectation des Membres
L’interface d’affectation affiche la liste des membres actifs disponibles. Le créateur peut affecter un testeur et plusieurs développeurs, ou retirer un membre existant. Chaque action déclenche l’envoi d’une notification email.
Figure 9 — Interface d’affectation des membres
5.5. Interface de Consultation des Projets Assignés
L’interface de consultation permet au testeur ou au développeur de visualiser uniquement les projets auxquels il est affecté, avec une recherche dynamique par nom.
Figure 10 — Interface de consultation des projets assignés
5.6. Interface de Supervision Admin
L’interface de supervision affiche la liste complète de tous les projets de la plateforme. Les boutons « Modifier » et « Fermer » sont activés uniquement pour les projets dont l’admin est le créateur
Figure 11 — Interface de supervision admin
6. Rétrospective du Sprint 2
Ce deuxième sprint a permis de réaliser l’ensemble des fonctionnalités planifiées avec succès : la création de projets avec statut automatique, la modification et la fermeture conditionnelle avec archivage complet, l’affectation et le retrait de membres avec notification automatique, la consultation des projets assignés avec filtre et recherche, ainsi que la supervision globale réservée à l’administrateur.
Conclusion
Ce deuxième sprint a permis de mettre en place le module central de la plateforme : la gestion des projets avec un cycle de vie précis, un contrôle strict des accès basé sur le rôle de créateur du projet, et des règles métier garantissant la qualité et la traçabilité (fermeture conditionnelle, archivage, interdiction de suppression, notification automatique). Ces briques constituent le socle sur lequel s’appuiera le Sprint 3, dédié à la gestion des tickets.
