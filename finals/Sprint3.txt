Chapitre 5 : Sprint 3 – Gestion des Tickets
Introduction
Ce chapitre présente les travaux réalisés dans le cadre du troisième sprint, consacré à la gestion des tickets. Ce module constitue le cœur fonctionnel de la plateforme : il couvre la création de tickets par les testeurs, le workflow d’assignation automatique aux développeurs, la validation par les gestionnaires, le suivi du cycle de vie, l’enregistrement du temps passé, ainsi que les commentaires et pièces jointes. Nous décrivons les diagrammes UML élaborés pour ce sprint et les interfaces développées.

2. Analyse et Conception
2.0. Règles métier
Le module de gestion des tickets repose sur un ensemble de règles métier précises qui gouvernent la création, l’assignation et le cycle de vie de chaque ticket.
Règle
Description
Création
Seul le testeur affecté au projet peut créer un ticket. Il renseigne : titre, description structurée (étapes, résultat attendu vs obtenu, notes), priorité, temps estimé, type (NOUVEAU ou RETOUR) et pièces jointes optionnelles.
Type RETOUR
Un ticket RETOUR est lié à un ticket parent (parent_ticket_id). Il est automatiquement assigné au même développeur que le ticket parent, sans passer par le workflow d’auto-assignation.
Auto-assignation
À la création d’un ticket NOUVEAU, le système propose automatiquement le développeur actif du projet ayant le moins de tickets OUVERT/EN_COURS. La proposition est soumise à validation par l’Admin ou le Chef de projet.
Ticket CRITIQUE
Si la priorité est CRITIQUE, force_assigned = true. Une notification urgente est envoyée aux gestionnaires pour validation accélérée.
Rejet d’assignation
Si l’admin rejette la proposition, le développeur est ajouté à rejected_by et une nouvelle proposition est calculée en excluant les développeurs déjà refusés. L’admin peut aussi assigner manuellement.
Cycle de vie
OUVERT → EN_COURS (développeur commence) → RESOLU (développeur termine) → FERME (testeur valide). Le premier ticket créé passe automatiquement le projet de « ouvert » à « en_cours ».
Suivi du temps
Seul le développeur assigné peut enregistrer du temps (logTime). Le champ temps_passe est incrémenté à chaque saisie. Le testeur est notifié à chaque enregistrement.
Pièces jointes
Formats acceptés : jpg, jpeg, png, pdf, doc, docx, mp4, mov. Taille maximale : 10 Mo par fichier.
Notifications
Chaque changement d’état, assignation ou enregistrement de temps déclenche une notification temps réel et/ou un email aux parties concernées.

2.2.1. Cas d’utilisation « Créer un ticket »
Cas d’utilisation : Créer un ticket
Sommaire d’identification
Titre
Créer un ticket
Description
Le testeur signale un bug en créant un ticket avec description structurée, priorité, temps estimé et pièces jointes optionnelles.
Acteurs
Testeur
Description des enchaînements
Pré-condition
Le testeur est authentifié, son compte est actif et il est affecté au projet.
Post-condition
Le ticket est créé avec l’état OUVERT. L’auto-assignation est déclenchée. Si le projet était « ouvert », il passe automatiquement en « en_cours ».
Scénario nominal
1. Le testeur accède au projet et clique sur « Créer un ticket ». 2. Il renseigne : titre, étapes pour reproduire, résultat attendu vs obtenu, notes, priorité, temps estimé, type NOUVEAU. 3. Il joint optionnellement des fichiers (images, PDF, vidéos). 4. Il soumet le formulaire. 5. Le système valide les données et crée le ticket (état : OUVERT). 6. Le système déclenche l’auto-assignation. 7. Si le projet est « ouvert », il passe automatiquement en « en_cours ». 8. Un message de confirmation est affiché.
Enchaînements alternatifs / Erreurs
E1 : Titre vide → « Le titre est obligatoire. » E2 : Temps estimé ≤ 0 → « Le temps estimé doit être positif. » E3 : Fichier > 10 Mo → « Fichier trop volumineux. » E4 : Testeur non membre du projet → HTTP 403.

2.2.2. Cas d’utilisation « Ticket de retour »
Cas d’utilisation : Créer un ticket de retour
Sommaire d’identification
Titre
Créer un ticket de retour
Description
Le testeur crée un ticket lié à un ticket parent dont la correction est insuffisante.
Acteurs
Testeur
Description des enchaînements
Pré-condition
Le ticket parent existe et possède un développeur assigné (assignment_status = approved).
Post-condition
Le ticket RETOUR est créé et directement assigné au développeur du ticket parent (force_assigned = true). Le développeur reçoit une notification.
Scénario nominal

Le système assigne directement ce développeur (assignment_status = approved, force_assigned = true). 5. Notification au développeur : « Un ticket de retour vous a été assigné d’office. »
Enchaînements alternatifs / Erreurs
E1 : Ticket parent sans développeur assigné → le workflow d’auto-assignation normal est déclenché.

2.2.3. Cas d’utilisation « Auto-assignation »
Cas d’utilisation : Auto-assignation d’un ticket
Sommaire d’identification
Titre
Auto-assignation d’un ticket
Description
Le système propose automatiquement le développeur le moins chargé du projet à l’admin pour validation.
Acteurs
Système (AutoAssignService), Admin, Chef de projet
Description des enchaînements
Pré-condition
Le ticket vient d’être créé (type NOUVEAU). Des développeurs actifs sont présents dans le projet.
Post-condition
proposed_developpeur_id renseigné, assignment_status = pending. L’admin reçoit une notification de validation.
Scénario nominal
1. Le système récupère les développeurs actifs du projet. 2. Il exclut ceux présents dans rejected_by. 3. Il sélectionne le développeur avec le moins de tickets OUVERT/EN_COURS. 4. Si priorité = CRITIQUE, force_assigned = true. 5. Mise à jour : proposed_developpeur_id = dev sélectionné, assignment_status = pending. 6. Notification Admin + Chef de projet : « Nouveau ticket, assignation proposée à [Nom] — en attente de validation. »
Enchaînements alternatifs / Erreurs
E1 : Aucun développeur actif → assignment_status = none + notification admin. E2 : Tous les devs dans rejected_by → même comportement que E1.

2.2.4. Cas d’utilisation « Validation / Réassignation »
Cas d’utilisation : Valider, rejeter ou réassigner un ticket
Sommaire d’identification
Titre
Valider, rejeter ou réassigner
Description
L’admin ou le chef de projet valide la proposition d’assignation, la rejette, ou assigne manuellement un développeur.
Acteurs
Admin, Chef de projet
Description des enchaînements
Pré-condition
assignment_status = pending (valider/rejeter) ou état quelconque (assigner manuellement). L’acteur est créateur du projet ou admin.
Post-condition (Valider)
developpeur_id = proposed_developpeur_id, assignment_status = approved. Notification + email au développeur et au testeur.
Post-condition (Rejeter)
Dev ajouté à rejected_by, assignment_status = rejected. Assignation manuelle requise.
Post-condition (Réassigner)
developpeur_id = dev choisi, force_assigned = true. Notification + email.
Enchaînements alternatifs / Erreurs
E1 : Rejet d’une assignation déjà approuvée → HTTP 409. E2 : Utilisateur choisi n’est pas un développeur → HTTP 400.

6. Rétrospective du Sprint 3
Ce troisième sprint a permis de livrer l’ensemble des fonctionnalités du module de gestion des tickets : création avec description structurée et pièces jointes, workflow d’auto-assignation avec validation par les gestionnaires, tickets de retour avec assignation directe, suivi du cycle de vie complet (OUVERT → EN_COURS → RESOLU → FERME), enregistrement du temps passé et système de commentaires.
Conclusion
Le Sprint 3 a concrétisé la fonctionnalité centrale de la plateforme : la gestion complète des tickets. Le workflow d’assignation automatique, combiné à la validation humaine des gestionnaires, garantit une répartition équilibrée de la charge entre les développeurs. Le cycle de vie structuré des tickets, depuis leur création par le testeur jusqu’à leur clôture après validation, assure une traçabilité totale. Ces bases solides permettront au Sprint 4 d’y greffer la couche d’Intelligence Artificielle pour l’analyse et la classification automatique des tickets.
