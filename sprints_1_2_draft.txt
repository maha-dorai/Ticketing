1342: Règles métier et cycle de vie du projet
1343: 
1344: Le cycle de vie d’un projet suit une progression stricte en trois statuts, décrits dans le tableau ci-dessous.
1345: Table 4.2: Cycle de vie d’un projet
1346: 
1347: Statut
1348: Déclencheur
1349: Description
1350: ouvert
1351: Création du projet
1352: Statut initial défini automatiquement à la création par le chef de projet ou l’admin.
1353: en_cours
1354: Premier ticket créé par un testeur
1355: Le système passe automatiquement le projet en « en_cours » dès qu’un testeur soumet un premier ticket.
1356: 
1357: Statut
1358: Déclencheur
1359: Description
1360: archivé
1361: Fermeture volontaire par le créateur
1362: Possible uniquement si tous les ti-ckets du projet ont le statut VALIDE. Le projet est archivé avec son histo-rique complet.
1363: 
1364: Les règles métier fondamentales régissant ce module sont les suivantes :
1365: 
1366: Un chef de projet peut consulter, modifier et fermer uniquement les projets qu’il a créés.
1367: 
1368: Un admin hérite de toutes les capacités d’un chef de projet et peut consulter l’ensemble des projets de la plateforme ; il ne peut modifier ou fermer que ses propres projets.
1369: La fermeture d’un projet est conditionnelle : tous les tickets du projet doivent avoir le statut VALIDE.
1370: Un projet archivé conserve son historique complet : date_debut, date_fin, membres participants, créateur, nombre de tickets.
1371: La suppression d’un projet est interdite pour garantir la traçabilité.
1372: 
1373: Un seul testeur peut être affecté à un projet. Plusieurs développeurs peuvent être affec-tés simultanément.
1374: Toute modification du projet (membres ou informations) déclenche une notification à tous les membres affectés.
1375: Le passage automatique au statut « en_cours » s’effectue lorsqu’un testeur crée le pre-mier ticket.
1376: Les règles métier associées au cycle de vie des tickets ne seront effectives qu'à partir du Sprint 3,
1377:  lors de l'implémentation du module de gestion des tickets. En conséquence, dans la version actuelle
1378:  de l'application, ces contraintes ne sont pas encore prises en compte

1441: Sommaire d’identification
1442: Titre
1443: Fermer un projet
1444: Description
1445: Ce cas décrit la fermeture et l’archivage d’un projet lorsque tous ses tickets sont validés.
1446: Acteurs
1447: Chef de projet (créateur), Admin (créateur)
1448: 
1449: Description des enchaînements
1450: Pré-condition
1451: Le projet est en statut « ouvert » ou « en_cours ». L’acteur est le créateur. Tous les tickets du projet ont le statut VALIDE.
1452: Post-condition
1453: Le statut du projet passe à « archivé ». Le projet est archivé avec : date_debut, date_fin (date de fermeture), liste des membres ayant participé, identité du créateur, nombre total de tickets. Aucun nouveau ticket ne peut être ajouté.
1454: Scénario nominal
1455: 1. L’acteur clique sur « Fermer le projet ». 2. Le système vérifie que tous les tickets sont en statut VALIDE. 3. Le système passe le statut à « archivé » et enregistre la date_fin. 4. Le projet apparaît en lecture seule dans la liste archi-vée avec son historique complet. 5. Un message de confirmation est affiché.
1456: Enchaînementsalter-natifs / Erreurs
1457: E1 : Des tickets ne sont pas encore VALIDE → « Impossible de fermer : X ticket(s) ne sont pas encore validés. » E2 : Acteur non créateur → HTTP 403

1465: Sommaire d’identification
1466: Titre
1467: Affecter des membres à un projet
1468: Description
1469: Ce cas décrit le processus d’affectation et de retrait de membres (testeur et développeurs) sur un projet, avec notification automatique.
1470: Acteurs
1471: Chef de projet (créateur), Admin (créateur)
1472: Description des enchaînements
1473: 
1474: Pré-condition
1475: Le projet existe avec le statut « ouvert » ou « en_cours ». Le créateur est au-thentifié. Les membres à affecter ont le statut « actif ». Le projet accepte au maximum un testeur actif. Toute tentative d’affecter un second testeur est re-jetée
1476: Post-condition
1477: Les membres sélectionnés sont associés au projet (table pivot project_user). Une notification est envoyée à tous les membres affectés. Les membres voient désormais le projet dans leur liste.
1478: Scénario nominal
1479: 1. L’acteur accède à la page de son projet. 2. Il clique sur « Affecter des membres ». 3. Le système affiche les utilisateurs actifs disponibles (testeurs et développeurs). 4. L’acteur sélectionne les membres et confirme. 5. Le sys-tème enregistre les associations dans project_user. 6. Le système envoie une notification à chaque membre affecté. 7. Un message de confirmation est affi-ché.
1480: Enchaînementsalter-natifs / Erreurs
1481: E1 : Compte désactivé → « Ce compte n’est pas actif. » E2 : Membre déjà affecté → « Ce membre est déjà affecté à ce projet. » E3 : Second testeur →
1482: « Un projet ne peut avoir qu’un seul testeur assigné. » Enchaînement alternatif
1483: — Retirer un membre : L’acteur clique sur « Retirer » à côté d’un membre. Le système supprime l’association et envoie une notification au membre retiré.

1589: Conclusion
1590: 
1591: Ce deuxième sprint a permis de mettre en place le module central de la plateforme : la gestion des projets avec un cycle de vie précis, un contrôle strict des accès basé sur le rôle de créateur du projet, et des règles métier garantissant la qualité et la traçabilité (fermeture conditionnelle, archivage, interdiction de suppression, notification automatique).
